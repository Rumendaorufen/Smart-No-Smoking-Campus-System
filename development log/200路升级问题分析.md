# 200+ 路摄像头升级问题分析

记录时间：2026-06-10
分析基准：当前 4 路摄像头架构

---

## 一、Python AI 引擎（web-flask）— 最严重

### 1. GPU 算力瓶颈
- `SmokingDetector` 全局单例，25fps 全帧推理，200 路时 GPU 队列无限堆积
- RTX 3060 12GB，级联检测每帧约 300ms，200 路轮训一次需 60 秒
- 帧缓冲 150 帧 × 2MB × 200 路 = 60GB，远超 16GB RAM
- **方向**：降采样到 2-3 FPS、多进程分片推理

### 2. Python GIL 多线程失效
- 当前每路 3 线程（reader + processor + watchdog），200 路 = 600 线程
- CPU/GPU 密集型任务下多线程无意义，线程切换开销反超计算
- **方向**：多进程替代多线程，每个进程独立 GPU 时间片

### 3. OpenCV RTSP 连接爆炸
- 单进程 200 路 `cv2.VideoCapture`，FFmpeg 解码器非大规模并发设计
- `pthread_frame.c` 断言失败率随路数增长
- **方向**：媒体网关剥离拉流（C++/Go），或引入 MediaMTX 代理

### 4. 磁盘 IO 写爆
- 多路同时报警时同步写磁盘：快照 JPG + mp4v 临时文件 + FFmpeg 转码 = 2 倍 IO 放大
- OpenCV mp4v 后转 H.264 产生双重写入
- 200 路 × 每天 ~20 次报警 × 5MB = ~20GB/天
- 无自动清理策略；确认的违规永久保留
- **方向**：FFmpeg pipe 直写 H.264 取消转码、分级证据策略（低置信度仅快照）、异步批量化刷盘

---

## 二、Java 中台（web-back）— 中度风险

### 5. Tomcat 线程池耗尽
- Spring Boot 默认最大线程 200，SSE/MJPEG 代理等长连接占住线程不释放
- 200 路上报 + 前端轮询 + SSE 流并发可耗尽线程池
- **方向**：调整线程池参数、Webflux 替代阻塞模型

### 6. 全量轮询带宽浪费
- 每 5 秒全量查 MySQL 返回 200+ 条设备状态，99% 数据未变
- 200 条 × 2.4KB × 12 次/分钟 ≈ 5.8MB/分钟
- **方向**：版本号 + 304 Not Modified、或 WebSocket 增量推送

### 7. Python 心跳密集
- 每个 StreamLoader 独立触发 `_update_db_status`（2-5 秒一次）
- 200 路高峰时 40-100 req/s 击穿 Java 接口
- **方向**：心跳合并去重，或批量上报

---

## 三、Vue 前端（web-vue）— 严重

### 8. MJPEG 长连接限制
- 浏览器单域名 6 并发 TCP 限制，MJPEG 是长连接，20+ 路画面空白
- **方向**：缩略图 JPG 定时刷新 + 点击后单路 MJPEG 详情

### 9. 侧边栏 UX 灾难
- 200 个 `device-nav-item` 无法滚动查找、搜索或分组
- **方向**：搜索/筛选/分页，或仅显示报警设备

### 10. SSE 消息列表内存泄漏
- AiChat.vue 的消息列表不做虚拟滚动，200+ 条后页面卡顿
- **方向**：虚拟滚动或分页加载

---

## 四、数据库/存储

### 11. MySQL 写争抢
- 默认 `sync_binlog=1`、`innodb_flush_log_at_trx_commit=1`
- 与证据文件写入争抢同一 SSD 的 IO
- **方向**：测试环境调低刷盘频率

---

## 五、核心根因链路

```
GPU 算力不够 → 推理延迟高 → 帧缓冲堆积 → 内存爆
                   ↓
              漏检/误报增多
                   ↓
              报警频率异常 → 磁盘 IO 压力 → MySQL 响应慢
                                   ↓
              前端轮询全量 ←── Java 线程排队 → WebSocket 延迟
                                   ↓
              前端 MJPEG 连接上限 → 画面空白
```

## 六、优先级路线

| 优先级 | 问题 | 方向 | 预计效果 |
|--------|------|------|---------|
| P0 | GPU 推理降采样 2-3 FPS | 帧计数器 skip | 容量翻 8-10 倍 |
| P0 | 前端 MJPEG 改缩略图 | 新增 thumb 接口 + 网格模式 | 突破 6 路限制 |
| P1 | 视频直写 H.264 | FFmpeg pipe 替代 mp4v | IO 减半 |
| P1 | 分级证据策略 | 置信度阈值决定录制级别 | 高峰期 IO 削峰 |
| P1 | 后端版本号/304 轮询 | ETag + 304 响应 | 轮询流量降 99% |
| P2 | 多进程分卡推理 | 按 camera_id 分片 | 进一步榨干 GPU |
| P2 | WebSocket 增量推送 | 替代轮询 + 兜底对账 | 实时零冗余 |
